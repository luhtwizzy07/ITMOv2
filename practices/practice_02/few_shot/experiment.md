- Артефакт Практики 1: ADR (редактируем исходный файл: practices/practice_01/adr.md)
- Что хотим улучшить: зафиксировать статус (accepted); добавить ≥3 содержательных альтернативы с trade-offs; явно описать OBS-1 (что логируем/не логируем); стратегию ошибок и таблицу маппинга LLM→HTTP (таймаут/исключения/ретраи/circuit breaker); принять решение по sync/async и целевой версии Python; явно задать интерфейс LLM-адаптера; перечислить риски и как их проверим. ## Решение
Выбрали async FastAPI с Python 3.10. Ввод/вывод по OUT-1. Перед LLM — санитайзинг (SEC-1). Ограничение diff ≤ 20 000 (API-1). Адаптер LLM с таймаутом 10s и ретраями x3 с jitter (REL-1). Логирование только request_id, длительность, статус (OBS-1).

## Запрос

Инструкция
Ты — архитектор и редактор ADR. Преобразуй «Исходный ADR» в «Улучшенный ADR» по правилам. Используй few-shot примеры ниже как эталон стиля и полноты.

Правила (обязательны)
- SEC-1: перед отправкой во внешний LLM из diff удаляются токены, пароли, приватные ключи
- API-1: diff > 20 000 символов → HTTP 413
- REL-1: таймаут LLM-вызова 10 секунд; ошибка конвертируется в контролируемый ответ
- OUT-1: ответ содержит summary, массив risks (≤3, поля file, line, evidence, risk) и массив checks
- OBS-1: логируем только request_id, длительность, статус; не логируем diff и ответы LLM

Критерии готовности Улучшенного ADR
1) Статус: accepted (дату и ответственных сохранить)
2) Явные решения с привязкой к SEC-1, API-1, REL-1, OUT-1, OBS-1
3) Выбор: async vs sync, целевая версия Python (конкретная), интерфейс LLM-адаптера (сигнатура)
4) Таблица маппинга ошибок LLM→HTTP (timeout, network/5xx, внутренняя ошибка)
5) Раздел OBS-1: что логируем и что не логируем
6) ≥3 альтернативы с краткими trade-offs
7) Риски и как их проверим (конкретные проверки)

Формат ввода
Вход: содержимое файла practices/practice_01/adr.md (Исходный ADR, правим его напрямую)

Формат вывода
Выход: полный обновлённый ADR (markdown), начиная с строки `# ADR: решение для первого рабочего сценария`.
