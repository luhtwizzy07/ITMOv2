# Проблема и метрики

## Проблема

- Пользователь: Клиент API, отправляющий diff для ревью
- Ситуация: Нужно получить структурированный отзыв по PR из diff
- Что происходит сейчас: Эндпоинт принимает произвольный dict, без схемы и валидации; diff без ограничений передаётся во внешний LLM; ошибки/таймауты LLM не обрабатываются; ответ не следует требуемому контракту OUT-1
- Почему это мешает пользователю или бизнесу: Возможны 500 при неверном входе или сбое LLM; риск утечки секретов (SEC-1); отсутствие лимитов приводит к 413/таймаутам и непредсказуемому времени ответа; клиенты не имеют стабильного контракта
- Что не входит в задачу: Изменение внешнего LLM; интеграция с GitHub; оптимизация качества генерации

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля запросов с корректным 422 при отсутствии поля diff | Базово: 0% (dict без схемы) | ≥ 95% | На тестовом стенде и в CI | Интеграционные тесты FastAPI |
| Доля запросов, завершающихся контролируемо при ошибке LLM | Базово: неизвестно/низко | ≥ 99% с маппингом ошибок на 5xx/4xx | В нагрузочных и отказных тестах | Логи статуса + интеграционные тесты |
| Доля запросов, отклонённых по длине diff > 20k | Базово: 0% | 100% с HTTP 413 | Валидационные тесты | Юнит/интеграционные тесты API |

## Почему изменение метрики подтвердит решение проблемы

Валидация входа и ограничение длины предотвращают 500 и соответствуют API-1. Обработка ошибок и таймауты обеспечивают контролируемый ответ по REL-1. Контракт ответа делает интеграцию предсказуемой и измеряемой через тесты.
