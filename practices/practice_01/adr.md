# ADR: решение для первого рабочего сценария

- Статус: accepted
- Дата: 2026-09-11
- Ответственные: Команда API, владелец продукта

## Контекст

Эндпоинт POST /api/reviews передаёт diff в внешний LLM через ReviewService без валидации, ограничений и обработки ошибок (см. TRAINING_PR.diff). Требуется соответствие правилам SEC-1, API-1, REL-1, OUT-1 и OBS-1.

## Решение

Выбрали async FastAPI на Python 3.10. Ввод/вывод строго по OUT-1. Перед отправкой в LLM выполняется санитайзинг секретов (SEC-1). Входной diff ограничен ≤ 20 000 символов, при превышении — HTTP 413 (API-1). Вызовы LLM идут через адаптер с таймаутом 10s, ретраями x3 с jitter и контролируемым маппингом ошибок (REL-1). Логирование соответствует OBS-1: пишем только request_id, длительность и статус; не логируем diff и ответы LLM.

### Интерфейс LLM-адаптера

```
generate(input: str, timeout_s: int = 10) -> dict { summary: str, risks: list, checks: list }
```

### Маппинг ошибок LLM → HTTP

| Ситуация | Код | Тело/сообщение |
|---|---:|---|
| Timeout ≥10s | 504 | { error: "LLM timeout" }
| Network/5xx LLM | 502 | { error: "LLM unavailable" }
| Внутренняя ошибка адаптера | 500 | { error: "Internal error" }

### Политика логирования (OBS-1)

- Логируем: request_id, длительность запроса, итоговый статус
- Не логируем: содержимое diff, prompt/response LLM, персональные данные

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Sync FastAPI + threadpool | Проще, но хуже масштабируется под I/O-bound и сложнее контролировать таймауты на уровне корутин |
| Делегировать предобработку клиенту | Нет контроля и несоответствие SEC-1/OBS-1; риск утечки секретов и логирования prompt/response |
| Полное логирование prompt/response | Нарушает OBS-1 и повышает риск утечки; юридические и операционные риски |

## Последствия и главный риск

- Положительные последствия:
  Повышение надёжности и предсказуемости ответов; соблюдение правил SEC-1, API-1, REL-1, OUT-1, OBS-1
- Ограничения:
  Возможна усечённость контекста diff; дополнительная задержка на санитайзинг
- Главный риск:
  Ложноположительное скрытие «секретов», ухудшающее качество ревью
- Как проверим риск:
  E2E-тест с синтетическим diff, содержащим паттерны секретов; убедиться, что [REDACTED] не мешает смыслу ревью
  Интеграционные тесты маппинга ошибок (timeout→504, 5xx→502, internal→500) и политики логирования (отсутствие prompt/response в логах)
