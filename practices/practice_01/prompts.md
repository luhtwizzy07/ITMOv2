## Master Prompt v1

Соберите здесь контракт второго запуска. Не копируйте все документы целиком — ставьте ссылки на файлы и переносите только необходимый для задачи контекст.

### 1. Цель и роль

- Цель: найти проблемы в `practices/practice_01/TRAINING_PR.diff`, заполнить все указанные файлы соответствующим образом
- Роль AI: ревьюер

### 2. Входы и источники

- Обязательный вход: `practices/practice_01/TRAINING_PR.diff`
- Разрешённые файлы и источники: Работаем только в директории `practices/practice_01` - из неё разрешены файлы `adr.md`, `analysis.md`, `context.md`, `P1-01_result.md`, `problem.md`, `product_management.md`, `project_management.md`, `prompts.md`, `tests_e2e.md`, `tests_integration.md`, `tests_load.md`, `tests_unit.md` и `TRAINING_PR.diff`
- Context Pack — факты, правила, примеры и ограничения:
    1. Задача помощника - для одного PR помощник получает diff и возвращает: 
        1. краткое описание изменения;
        2. не больше трёх рисков с файлом, строкой и доказательством;
        3. список проверок, которые стоит запустить.

    2. Решение всегда принимает человек. Помощник не может approve, merge или менять код.

    3. Правила репозитория:

        - `SEC-1`: перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи.
        - `API-1`: diff длиннее 20 000 символов отклоняется с HTTP 413.
        - `REL-1`: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ.
        - `OUT-1`: ответ содержит `summary`, массив `risks` и массив `checks`. В `risks` максимум три элемента с полями `file`, `line`, `evidence`, `risk`.
        - `SCOPE-1`: сервис только советует; он не пишет код и не выполняет действия в GitHub.
        - `QA-1`: риск включается в ответ, только если он подтверждён строкой diff или правилом репозитория.
        - `OBS-1`: в лог пишутся только `request_id`, длительность и статус. Содержимое diff и ответа модели не логируется.

    4. Примеры комментария:

        - Хороший:

            ```text
            app/review_service.py:16 — diff отправляется во внешний LLM без удаления секретов,
            что нарушает SEC-1. Проверка: передать diff с тестовым token и убедиться,
            что в prompt осталось [REDACTED].
            ```

        - Плохой:

            ```text
            Код можно улучшить. Добавьте тесты и обработку ошибок.
            ```

### 3. Задача и артефакты

- Что сделать: найти проблемы в `TRAINING_PR.diff`, заполнить указанные файлы следующим образом:

1. `context.md` - AS IS: продуктовый и командный контекст, источники и ограничения
2. `problem.md` - пользователь, проблема и измеримые продуктовые метрики
3. `analysis.md` - AS IS и TO BE процесса в выбранной нотации
4. `product_management.md` - use cases, user stories и сценарии
5. `project_management.md` - инкременты, роли людей/AI и план поставки
6. `adr.md` - архитектурное решение и Mermaid-схема
7. `tests_unit.md` - unit-проверки
8. `tests_integration.md` - integration-проверки
9. `tests_load.md` - нагрузочные проверки и ожидаемые пределы
10. `tests_e2e.md` - сквозные сценарии
11. `prompts.md` - запросы, результаты, ссылки на изменённые артефакты и собственная оценка (не заполнять Peer review)

Необходимо заполнять эти файлы в соответствии с теми шаблонами для записи ответов, которые в них уже есть (таблицы, поля для ответов и т.д.)
- Что вернуть: список проблем, обнаруженных в ходе анализа `TRAINING_PR.diff`, а также статус заполнения всех 11 вышеупомянутых итоговых файлов

### 4. Формат результата

- Структура ответа:

1. Список найденных проблем должен быть строго структурирован с доказательствами в формате файл:строки diff 
2. Необходимо заполнять указанные 11 файлов по их шаблонам

- Ограничения объёма:
1. Лаконичное описание проблемы из diff и компактное доказательство 
2. В итоговых файлах не создавать лишние разделы

### 5. Полномочия и запреты

- Разрешено: анализировать diff, изменять итоговые 11 файлов (но придерживаясь их исходного шаблона)
- Запрещено: как-либо взаимодействовать со всеми остальными, не упомянутыми ранее файлами, придумывать факты

### 6. Рабочий процесс и остановка

- Шаги: Прочитать `TRAINING_PR.diff` → Извлечь необходимую информацию из него → Составить список найденных проблем с доказательствами → Заполнить 11 итоговых файлов
- Когда остановиться и запросить человека: Если требуется информация не из разрешённых источников

### 7. Проверки и evidence

- Как проверять утверждения: каждой найденной проблеме должна соответствовать реальная строка из `TRAINING_PR.diff`
- Какое evidence сохранить: `file:line` из `TRAINING_PR.diff`, правило из Context Pack

### 8. Definition of Done

- Задача закончена, когда: сформирован список найденных в diff проблем вместе с доказательствами, все 11 итоговых файлов полностью заполнены нужным образом

## Сравнение двух запусков

| Проверка | Zero-shot | С master prompt | Вывод команды |
|---|---|---|---|
| Есть ссылка на файл или строку | Да (см. P1-01_result.md) | Да (везде указаны file:line) | Вывод содержит точные ссылки на строки diff в risks и evidence |
| Вывод подтверждён diff или правилом | Да (основные пункты) | Да (каждый риск опирается на SEC-1/API-1/REL-1 и строки diff) | Вывод опирается на конкретные строки TRAINING_PR.diff и правила Context Pack |
| Соблюдены границы AI | Да | Да | Сервис только советует; не модифицирует код/PR; за человеком решение |
| Есть воспроизводимая проверка | Да (частично) | Да (добавлены шаги проверок) | Для каждого риска добавлены проверочные шаги (422, 413, таймаут, секреты) |
