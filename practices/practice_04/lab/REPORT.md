## ДЗ: среда, skill и собственный MCP

Решение по ревью: замечания explore сверены с кодом и контрактом и отклонены
как неподтверждённые. Например, import service и setUp присутствуют, повторная
отписка действительно ожидает false, аннотации публичной функции есть.
Полная сверка — [evidence/review-decision.md](evidence/review-decision.md).

| Критерий из условий | Баллы | Реализация и подтверждение |
|---|---:|---|
| AGENTS.md применяется | 1 | Чтение правил в environment.jsonl и b-agent-verified.jsonl; прежний контракт сохранён |
| Skill применяется | 1 | Штатный вызов skill, чтение ресурса, gate RED/GREEN A и B |
| MCP применяется | 1 | notify_checks_project_check в environment-continued.jsonl и при проверке B |
| Hook применяется | 1 | Реальные edit с AUTO-CHECK FAIL и PASS в hook-*.jsonl |
| Обоснованы подключения | 1 | README и пояснение ниже |
| Skill содержит автоматизацию и понятен | 1 | phase.py проверяет результаты unittest, tests/test_skill.py проверяет отказ на ложном RED |
| Skill запущен, результат проверен | 1 | a/b-red/green.json и b-agent-acceptance.jsonl |
| Собственный MCP tool полезен | 1 | project_check запускает единый runner по фиксированному профилю |
| MCP реально вызван; проверен ошибочный вход | 1 | mcp.json: успех, неизвестный профиль, неверный тип; test_tools.py использует настоящий stdio |
| Конкретная рефлексия | 1 | reflection.md: перенос конфигурации, версия OpenCode, остановки модели, ошибка B |

Это соответствие критериям, а не обещание оценки преподавателя.

Правила фиксируют контракт и запрещают раздувать маленькую задачу. Skill делает
порядок работы проверяемым. MCP предоставляет один интерфейс проверок, исключая
неизвестные команды и пути. Hook возвращает результат проверки в вывод записи,
чтобы следующая итерация агента учитывала реальную ошибку. Для учебного сервиса
дополнительные GitHub/браузерные MCP не нужны: собственный tool применён и в
среде, и в части ДЗ про MCP. Создание отдельного профиля субагента необязательно;
использован готовый explore для отдельного ревью.

## Как устроен собственный skill

notify-tdd связывает требования к фиче с тестами и исполняемым gate phase.py.
Gate отдельно запускает baseline и выбранную фичу, затем разбирает объект
unittest.TestResult, а не только код завершения команды. RED принимается при
assertion failures фичи и рабочем baseline, но отклоняется при ошибках загрузки,
skip и отсутствии тестов. GREEN требует прохождения обоих наборов; общий runner
дополнительно проверяет взаимодействия фич и инструментов среды.

## Как устроен собственный MCP

mcp_server.py использует официальный SDK и stdio. Единственный tool:
`project_check(profile: str = "all")`. Допустимы baseline, a, b, all; команды
фиксированы в scripts/check.py. На неизвестном профиле subprocess не запускается.
Успех возвращает PASS и exit_code 0; неуспешный тест — FAIL и реальный вывод;
таймаут 60 секунд превращается в явную ошибку tool. Неверный тип отвергается SDK.

scripts/prove_mcp.py выполняет initialize, tools/list и три настоящих tools/call
через официальный клиент. В evidence/mcp.json сохранены параметры и ответы.
Тесты среды также проверяют, что ошибка теста не превращается в PASS, таймаут
виден вызывающему, а неизвестный профиль не запускает команду.

## Воспроизведение и показ

Из этой папки: make setup, make test, make mcp-proof. Для живого показа OpenCode:
opencode --model ollama/itmo-agent --agent build. Загрузи notify-tdd, вызови
notify_checks_project_check для baseline и not-a-profile. Для демонстрации hook
временно измени ожидание одного теста инструментом edit, затем восстанови его.
После показа обязательно выполни make test и проверь diff.

Markdown выбран как разрешённый условиями формат. Журналы JSONL содержат реальные
события инструментов с входом, выходом и sessionID. Они не являются пересказом
или синтетическим примером. Абсолютные локальные пути в журналах — исторические;
для повторного запуска нужны относительные команды из README, а не эти пути.
